## この本について

「クリーンアーキテクチャというアーキテクチャは存在しない」と言われることがあります。私もこの言葉に賛成です。同心円の図をそのまま写しても、動くサービスは出てきません。あの図が教えてくれるのは依存の向きという原則だけです。レイヤーをいくつ作るか、interface をどこに置くか、DB への依存をどこまで剥がすか。そこは全部自分で判断するしかありません。

この本は、Go でサービスを設計・運用する中でこれまでに疑問に思い調べてきた、「自分で判断するしかない部分」の判断基準をまとめたものです。元になっているのは Zenn に公開してきた設計に関する記事群です。ただし単に束ねたのではなく、原則から実践へ一本の流れになるよう構成を組み直しました。記事間で揺れていた用語の統一と、誤りの修正も行っています。

ゴールは、読み終えたとき、自分のサービスを設計し、壊れ方を観測しながら運用できる状態になることです。そのため、第8部では読書ログサービスを題材に、設計から最小構成での実装、本番運用に向けた検討までをつなぎます。

## 対象読者

- Go の基本文法を理解していて、次は設計を学びたい方
- クリーンアーキテクチャや DDD の本を読んだものの、自分のコードにどう落とすか迷っている方
- レイヤー分割や interface の置き場所について、チームで根拠を持って説明したい方

逆に、GoF デザインパターンの網羅的な解説や、特定フレームワークの使い方はこの本には書いていません。

## 本書の構成

全26章は、はじめにとおわりにを含む8つの部に分かれています。

| パート | 章 | 内容 |
| --- | --- | --- |
| 第1部 設計の原則 | 第1〜5章 | アーキテクチャの選び方、依存性ルールとその検査、モジュール構造 |
| 第2部 境界を設計する | 第6章 | モジュールからサービス境界への分割判断 |
| 第3部 ドメインを守る | 第7〜10章 | 値オブジェクト、集約、ドメインイベント、腐敗防止層 |
| 第4部 アプリケーションを組み立てる | 第11〜17章 | UseCase、interface、Repository、トランザクション、バリデーション、エラー、DI |
| 第5部 処理とプロセスの境界 | 第18〜19章 | Context による処理の寿命、Outbox、再送、冪等性 |
| 第6部 観測可能なサービスを作る | 第20章 | Logs・Metrics・Traces による観測可能性 |
| 第7部 設計を維持する | 第21〜22章 | テスト戦略と設計ルールの継続的な検証 |
| 第8部 ハンズオン | 第23〜26章 | 読書ログサービスの設計、実装、本番運用の視点とおわりに |

前から順に読む想定で書いていますが、各章は独立して読めるようにも作ってあります。いま悩んでいるテーマの章から読み始めて構いません。ただし第2章のアーキテクチャの選び方と第3章の依存性ルールは、他の章の前提になるので先に読むことをおすすめします。

全体は、設計原則と依存方向から始めて、モジュール境界・サービス境界・ドメイン・アプリケーションへ進みます。続いて、処理の寿命・分散システム・Observability・設計の維持を扱い、最後に1つのサービスで総合演習に取り組みます。各章では、その設計が何を防ぎ、何を保証しないかを分けて書いています。本書での選択や私の経験則は、言語やデータベースの仕様とは区別して示します。

## 用語の統一

元記事では表記が揺れていた用語を、本書では次のように統一します。

| 本書での表記      | 意味                                                              |
| ----------------- | ----------------------------------------------------------------- |
| domain 層         | エンティティ、値オブジェクト、Repository interface を置く最内層   |
| UseCase 層        | アプリケーションロジックを置く層。ディレクトリ名は `usecase/`     |
| Interactor        | UseCase 層の実装 struct。`CreateOrderInteractor` のように命名する |
| interface 層      | HTTP ハンドラなど外部との境界。ディレクトリ名は `interface/`      |
| infrastructure 層 | DB 実装や外部 API 連携などの技術詳細                              |

層の名前としては「UseCase 層」、その実装 struct の名前としては「Interactor」を使います。クリーンアーキテクチャの原典では Use Cases 層の実装を Interactor と呼んでおり、本書もそれに合わせました。

## サンプルコードの前提

サンプルコードは Go 1.22以降を前提にしています。コード例は本書のために書き下ろしたもので、説明に必要な部分以外は省略しています。エラーハンドリングも、章の主題に関係しない箇所では簡略化しています。

動かして確かめられるコードは、2つのリポジトリに分けて公開しています。[go-service-design-examples](https://github.com/135yshr/go-service-design-examples) には、読書ログサービス（`booklog`）と、Outbox と冪等な Consumer の実装（`idempotency`）があります。[depcheck](https://github.com/135yshr/depcheck) は、第4章で使う、依存の向きを検査するツールです。本文は、章ごとに、どのコードのことかを示します。必要な Go のバージョンは、`booklog` が 1.22 以降、`idempotency` が 1.25 以降、`depcheck` が 1.26 以降です。

本書では、第4章から、読書ログサービスを共通の例として使います。本の読書状況を記録し、読了をきっかけに後続の処理を行う、小さなサービスです。モジュールは `book`、`reading`、`review`、`user` の4つを想定します。第5章でモジュールの分け方を見て、第23章で改めて設計します。章によっては、読書ログサービス以外の例（注文や決済など）も使います。

それでは、同心円の図の話から始めます。
