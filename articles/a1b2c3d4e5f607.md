## はじめに

以前、MarkdownをPDFに変換するCLIツール **md2pdf** を作りました。

https://github.com/135yshr/md2pdf

Markdownから、

- GitHub風のスタイル
- Mermaid
- 日本語
- テーブル
- コードブロック

などを含んだPDFを生成できます。

例えば、

```sh
md2pdf report.md
```

で、

```text
report.md
   ↓
report.pdf
```

となります。

これはこれで便利なのですが、実際に仕事で使おうとすると一つ問題が出てきました。

**PDFのデザインを変更したくなります。**

社内ドキュメントならGitHub風でも問題ありません。

しかし、

- 顧客へ提出するレポート
- セキュリティ診断報告書
- 技術提案書
- 社内標準フォーマット
- 自社ブランドのドキュメント

となると、

> Markdownは同じままで、見た目だけ変えたい

という要求が出てきます。

そこでmd2pdfに **Custom CSS機能** を追加しました。

```sh
md2pdf -css brand.css report.md
```

これで、Markdownを変更せずにPDFのデザインを変更できます。

## Markdownにデザインを持ち込まない

今回一番やりたかったのはこれです。

Markdown側にはできるだけ「意味」だけを書きます。

```markdown
# Security Assessment Report

## Executive Summary

今回の調査では3件のHighリスク項目を確認しました。

## Findings

| Severity | Finding |
| --- | --- |
| High | SQL Injection |
| Medium | Missing CSP |
```

ここに、

```html
<div class="red-title">
```

のような見た目のためのHTMLを入れ始めると、Markdown自体が特定の出力形式に依存してしまいます。

理想としては、

```text
Content
   ↓
Markdown

Design
   ↓
CSS
```

と分離したいところです。

そこで、

```sh
md2pdf -css report.css report.md
```

という形にしました。

## 基本的な使い方

例えば次のCSSを用意します。

```css
body {
  font-family: "Noto Sans CJK JP", sans-serif;
  font-size: 11pt;
  line-height: 1.7;
}

h1 {
  font-size: 28pt;
  border-bottom: 4px solid #333;
  padding-bottom: 8px;
}

h2 {
  margin-top: 2em;
  border-left: 5px solid #333;
  padding-left: 12px;
}

table {
  width: 100%;
}

th {
  font-weight: 700;
}
```

そして、

```sh
md2pdf -css report.css report.md
```

とします。

Markdown本文は一切変更せず、PDFだけデザインを変更できます。

## CSSは組み込みスタイルの後に適用する

md2pdfには元々GitHub風のCSSがあります。

Custom CSSを指定した場合は、

```text
built-in CSS
    ↓
custom CSS
```

の順番で適用します。

つまりCSSのCascadeをそのまま使います。

例えば組み込みCSSに、

```css
h1 {
  font-size: 2em;
}
```

があったとしても、

```css
h1 {
  font-size: 32px;
}
```

とCustom CSS側で指定すれば、こちらが優先されます。

既存スタイルを全部書き直す必要はありません。

変更したい部分だけ上書きできます。

## CSSを複数指定できるようにした

もう一つ追加したのが、`-css` を複数指定できる機能です。

```sh
md2pdf \
  -css company.css \
  -css customer.css \
  report.md
```

適用順は、

```text
Built-in CSS
      ↓
company.css
      ↓
customer.css
```

です。

後から指定したCSSが優先されます。

これは実際の業務を想定するとかなり便利です。

例えば、

```text
styles/
├── company.css
├── security-report.css
├── customer-a.css
└── customer-b.css
```

としておけば、

```sh
md2pdf \
  -css styles/company.css \
  -css styles/security-report.css \
  -css styles/customer-a.css \
  report.md
```

のようにできます。

つまり、

```text
会社共通
   +
文書種類
   +
顧客固有
```

というレイヤーでスタイルを管理できます。

CSSのCascadeと非常に相性がいい構成です。

## HTML出力も追加した

Custom CSSを実装してすぐ気付いた問題があります。

PDFでCSSを調整するのは面倒です。

```text
CSS変更
 ↓
PDF生成
 ↓
PDFを開く
 ↓
確認
 ↓
CSS変更
```

というループになります。

そこで、

```sh
md2pdf -format html document.md
```

というHTML出力も追加しました。

```sh
md2pdf \
  -format html \
  -css report.css \
  report.md
```

とすると、`report.html` が生成されます。

これをブラウザで開いて、CSSを変更してリロードすれば、

```text
CSS変更
 ↓
Browser Reload
 ↓
確認
```

となります。

完成したら、

```sh
md2pdf -css report.css report.md
```

でPDFを作ります。

## HTMLとPDFで同じCSSを使う

この仕組みで重要なのは、HTMLとPDFで同じCSSを使うことです。

md2pdfのPDF生成は概ね、

```text
Markdown
   ↓
goldmark
   ↓
HTML
   ↓
CSS
   ↓
Chromium
   ↓
PDF
```

という仕組みです。

HTML出力は途中で止めるだけです。

```text
Markdown
   ↓
goldmark
   ↓
HTML + CSS
   ↓
report.html
```

そのため、

```sh
md2pdf -format html -css report.css report.md
```

で確認したHTMLと、

```sh
md2pdf -css report.css report.md
```

で作るPDFは、基本的に同じレンダリング元を使います。

「PDF専用のテンプレートエンジン」を別に持たなくてよいのも、この方式の利点です。

## Chromiumを直接操作する

md2pdfの初期バージョンではPDF生成にPython + Playwrightを使っていました。

現在はGoからChromium DevTools Protocolを直接操作しています。

概念的には、

```text
Markdown
 ↓
HTML
 ↓
CSS
 ↓
Chromium
 ↓
Page.printToPDF
 ↓
PDF
```

です。

つまりPDF生成と言っても、実際には、

> Webページを作ってChromiumで印刷する

という考え方です。

そのため、CSSとの相性が非常に良いです。

## 例えば社内ブランド用PDFを作る

例えば会社の資料用に、

```css
:root {
  --primary: #1f4e79;
  --border: #d0d7de;
}

body {
  font-family: "Noto Sans CJK JP", sans-serif;
}

h1 {
  color: var(--primary);
  border-bottom: 3px solid var(--primary);
}

h2 {
  color: var(--primary);
}

blockquote {
  border-left: 4px solid var(--primary);
  background: #f6f8fa;
  padding: 12px 16px;
}

table {
  border-collapse: collapse;
}

th {
  background: var(--primary);
  color: white;
}
```

のようなCSSを作っておけば、

```sh
md2pdf -css company.css proposal.md
```

だけで共通デザインのPDFを作れます。

## 顧客ごとに変更する

さらに、

```css
/* customer-a.css */

:root {
  --primary: #8b0000;
}
```

のような差分CSSを用意すれば、

```sh
md2pdf \
  -css company.css \
  -css customer-a.css \
  proposal.md
```

とできます。

Markdownをコピーする必要はありません。

```text
proposal.md
     │
     ├─ company.css + customer-a.css
     │        ↓
     │   Customer A PDF
     │
     └─ company.css + customer-b.css
              ↓
         Customer B PDF
```

同じ内容から複数ブランドの成果物を生成できます。

## MarkdownとCSSをGitで管理する

この形にすると、MarkdownだけでなくデザインもGitで管理できます。

```text
docs/
├── report.md
└── styles/
    ├── base.css
    ├── security.css
    └── customer-a.css
```

変更履歴も、

```diff
 h1 {
-  font-size: 24px;
+  font-size: 28px;
 }
```

のように普通のコードレビューで確認できます。

バイナリのWordテンプレートやPDFテンプレートとは違い、デザイン変更自体もdiffでレビューできます。

これはDocs as Codeとの相性がかなり良いと思っています。

## CIでPDFを生成する

MarkdownとCSSをGit管理しているので、CIにも載せやすくなります。

例えばイメージとして、

```yaml
- name: Build report
  run: |
    md2pdf \
      -css styles/company.css \
      -css styles/report.css \
      report.md
```

とすれば、

```text
Markdown
   +
CSS
   +
Git
   ↓
CI
   ↓
PDF Artifact
```

という構成になります。

つまり、文書作成もソフトウェアのビルドに少し近づきます。

## AI時代のドキュメント生成とも相性がいい

この機能を作っていて、以前より価値が大きくなっていると感じた点があります。

最近はAI Coding AgentやLLMに、

- 設計書
- 調査報告
- ADR
- セキュリティレポート
- 実装計画

などを書かせる機会が増えています。

AIにWord文書やPDFそのものを作らせることもできますが、個人的には、

```text
AI
 ↓
Markdown
 ↓
Review
 ↓
Renderer
 ↓
PDF
```

という構成の方が扱いやすいと感じています。

MarkdownならGit diffでレビューできます。

出力の見た目はCSS側で制御できます。

つまり、

```text
AI = Content
CSS = Presentation
Git = Review / History
md2pdf = Renderer
```

という役割分担です。

AIに毎回「この色にして」「この余白にして」と指示する必要もありません。

AIには内容を書かせて、デザインは決定論的なCSSに任せられます。

## `</style>` を含むCSSは拒否する

Custom CSSを追加すると、一つ注意点があります。

md2pdfではCSSをHTML内の `<style>` にインライン展開しています。

つまり、CSSファイルに、

```html
</style>
```

が含まれていると、style要素を閉じてHTMLを挿入できてしまいます。

そこで現在は、`</style` を含むCSSをエラーにしています。

CSSとして通常必要になる文字列ではないため、曖昧にエスケープするよりも明示的に拒否する方針にしました。

こういう部分は、単純な「CSSファイルを読み込む機能」でも、実装してみると意外と考えることがあります。

## DOCXとConsoleは別の仕組み

なおCustom CSSは、PDFとHTMLに適用します。

DOCXはPandocのreference document、ConsoleはGlamourのstyleを使っているため、それぞれ別の仕組みです。

現在のmd2pdfは、

```text
                  ┌─ PDF ─── CSS
                  │
Markdown ─────────┼─ HTML ── CSS
                  │
                  ├─ DOCX ── reference.docx
                  │
                  └─ Console ─ Glamour Style
```

という構成になっています。

出力形式に無理やり共通のスタイル機構を押し込まず、それぞれに適した仕組みを使っています。

## md2pdfが目指しているもの

最初にmd2pdfを作ったときは、

```text
Markdown → PDF
```

だけを考えていました。

しかし実際に使っていくうちに、

```text
                   ┌─ Terminal
                   │
Markdown ──────────┼─ HTML
                   │
                   ├─ PDF
                   │
                   └─ DOCX
```

になってきました。

さらに今回、

```text
Content
   ↓
Markdown

Presentation
   ↓
CSS / Style
```

も分離できるようになりました。

なので最近は、md2pdfを単なるPDFコンバーターというより、

> Markdownを原本として、用途に応じた成果物を作るCLI

として考えるようになっています。

名前は完全に `md2pdf` なのですが。

## まとめ

md2pdfにCustom CSS機能を追加しました。

```sh
md2pdf -css report.css report.md
```

さらにCSSは複数指定できます。

```sh
md2pdf \
  -css company.css \
  -css customer.css \
  report.md
```

HTMLでプレビューもできます。

```sh
md2pdf \
  -format html \
  -css report.css \
  report.md
```

今回の機能によって、

```text
Markdown = 内容
CSS      = デザイン
Git      = バージョン管理
md2pdf   = レンダリング
```

という構成が取れるようになりました。

特にAIでMarkdownを生成する機会が増えている今、**内容の生成と成果物のデザインを分離する**ことには以前より意味があると思っています。

Markdownでドキュメントを管理しつつ、顧客向け・社内向けのPDFも同じソースから作りたい方は、よければ試してみてください。

https://github.com/135yshr/md2pdf

```sh
brew install 135yshr/tap/md2pdf
```
