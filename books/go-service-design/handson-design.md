## 第23章：何を一緒に変更するかを考える

ここからの3章では、同じ読書ログサービスを設計し、最小限の実装を読み、運用上の故障を考えます。題材は、本とその読書状況を記録し、読了をきっかけに後続処理を行うサービスです。最初から複数のサービスに分けず、1つのプロセスと1つのデプロイ単位から始めます。

別途用意する `example/booklog` は、本書の設計をすべて実装した製品ではなく、読了処理とイベント配送を学ぶための小さなサンプルです。本章では将来の候補とサンプルの範囲を区別します。実際のサンプルは `books/go-service-design/example/booklog` にあります。

## 利用者の操作と境界の候補

まず、実現したい操作を挙げます。

- 本の情報を登録し、参照します。
- 読書記録を開始し、読了します。
- 読了後に感想を書きます。
- 利用者ごとに読書記録を参照します。
- 読了を契機に、通知や集計などの後続処理を行います。

これらから、次の4つをモジュールの候補として考えます。ここでいうモジュールは責務の区切りであり、Go module や独立したサービスを必ず意味するものではありません。

| 候補      | 責務                             | 主な境界                                   |
| --------- | -------------------------------- | ------------------------------------------ |
| `book`    | 本の識別と書誌情報               | 読書状態を持ちません                       |
| `reading` | 誰が何を読んでいるか、読了の判断 | 読書状態の不変条件を守ります               |
| `review`  | 感想の作成と参照                 | 読了済みかの確認方法を決める必要があります |
| `user`    | 利用者の識別や認証               | 他のモジュールに認証の実装を漏らしません   |

これらは業務上の境界の仮説です。最初から4つのデータベースやネットワーク API を用意する理由にはなりません。変更理由、担当チーム、アクセス制御、負荷や整合性の要求を観察します。必要が生じたら境界を見直します。

サンプルで中心になるのは `reading` です。`book`、`review`、`user` の完全な機能、認証、外部書誌 API、通知や永続 DB は対象外です。識別子が登場しても、対応するモジュール全体が実装済みという意味ではありません。

## Reading 集約と読了

`Reading` は、1件の読書記録の状態を管理する集約ルートです。読了操作では少なくとも次を守ります。

1. 対象の記録が存在し、読了可能な状態であることを確認します。
2. 読了状態を更新します。読了日時を扱う場合は、状態と日時を一緒に更新します。
3. 読了が成功したら `ReadingCompleted` を生じさせます。
4. 失敗した操作では状態の更新もイベントの記録も確定しません。

二重の読了要求をどう扱うかは API の契約として決めます。状態遷移の拒否と、同じ操作の再試行を同じ結果として返すことは別の設計です。単に事前に検索するだけでは、並行要求による二重更新を防げません。永続 DB ではロックやバージョンによる競合検出なども必要です。

サンプルの `Reading` は ID と読了状態に絞り、読了日時は実装していません。`ReadingCompleted` は読了成功時にユースケースが Outbox へ記録します。

`review` を実装する場合は、「読了前に感想を書けない」というルールをどこで確認するかも決めます。別モジュールへの問い合わせだけでは不十分な場合があります。確認から保存までの間に状態が変わり得るためです。読了を取り消せるか、どの程度の整合性を必要とするかを含めて設計します。サンプルに感想機能があるとは仮定しません。

## 最初は modular monolith

1つのアプリケーション内で責務を分ける構成を、ここでは modular monolith と呼びます。分割候補を明示しつつ、サンプルでは必要な範囲のみを実装します。`reading` の状態変更はその集約を通し、HTTP やインメモリ保存の詳細をドメインに持ち込みません。

```text
HTTP → 読了ユースケース → Reading
                  ↓
       トランザクション境界
          ├── 読書状態を保存
          └── Outbox にイベントを記録
                  ↓
            配送 worker → Consumer
```

矢印は処理の流れであり、すべてが別プロセスであることを示しません。ユースケースは必要な保存操作の契約に依存し、具体的なインメモリ実装と HTTP、worker の配線はアプリケーションの起動側で行います。ドメイン自体は HTTP、`context.Context`、ログやトレース SDK に依存させません。

読書状態と Outbox を同じトランザクションで確定するのは、保存成功後にイベント送信だけが失敗する問題を避けるためです。後続処理には重複が届き得るので、Consumer 側でも対策します。Outbox は配送の一度きりの成功を保証する仕組みではありません。

## エラーと設計の検証

HTTP の入力形式、存在しない記録、許されない状態遷移、内部障害は区別します。HTTP 層は外部向けの応答に変換し、内部エラーや機密情報をそのまま返さないようにします。具体的なステータスコードと応答形式は、実装の契約を確認してください。

設計を検証する際には、正常な読了だけでなく、対象がない場合、読了できない状態、途中の保存失敗、同時実行、イベントの再配送を考えます。インメモリ保存は手軽ですが、プロセス終了でデータが失われます。永続化や障害復旧を検証するには、実際に採用する DB と配送基盤で別途テストが必要です。

次章では `Reading`、`CompleteReading`、インメモリのトランザクションと HTTP のつながりを追います。第25章では同じ流れに処理寿命、配送、観測を重ねます。
