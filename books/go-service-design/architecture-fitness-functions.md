## 設計判断を検証可能にする

Architecture Fitness Function は、設計上の望ましい性質が維持されているかを繰り返し評価する仕組みです。テストや静的解析に限らず、運用時の計測も含みます。「きれいな構成」を一度判定するのではなく、変更に伴って境界や実行時の性質が崩れていないかを確かめます。

設計ルールは、次の順に強くしていきます。最初はレビュー時の注意事項として言葉で共有します。次に、同じ指摘が繰り返されるルールを自動の検査にします。最後に、その検査を CI で毎回実行します。アーキテクチャは作って終わりではなく、変更のたびに維持するものだからです。ただし、すべてのルールを自動化できるわけではありません。検査で分かることと分からないことを、ルールごとに書き分けます。

例えば読書記録サービスでは、記録の保存と通知の配信に対して次のようにルールを具体化します。条件、観測方法、失敗時の対応をセットで決めると、レビューだけに頼らず運用できます。

| 守りたい性質 | 検証方法の例 | 検査だけでは分からないこと |
| --- | --- | --- |
| 内側から外側に依存しない | import の検査 | interface の責務が適切か |
| 他モジュールの内部を直接参照しない | import の許可リストと契約テスト | 公開 API の意味が適切か |
| キャンセルと期限を伝播する | analyzer とキャンセルのテスト | 全経路で処理が速やかに終わるか |
| 状態と Outbox を一緒に保存する | 実 DB の障害注入テスト | 外部への一度だけの配信 |
| 障害を追跡できる | trace の伝播テストと運用時の計測 | 計測から原因を特定できるか |

## 依存方向とモジュール公開面

第4章の `go list` による直接 import の検査を起点に、依存を許す方向をルールとして記録します。`domain` は同じ業務モジュールの `usecase` や `adapter` を参照しない、`usecase` は `adapter` を参照しない、という具合です。外側から内側へ向かう import は許可します。Go は循環 import を拒否しますが、循環のない逆方向依存は拒否しません。

`go list -json ./...` の `ImportPath` と `Imports` を使えば、ビルド対象のパッケージと直接依存を機械的に取得できます。間接依存を制限したい場合は `Deps` を別のルールとして評価します。間接依存の禁止は第三者ライブラリを経由した依存も対象になるため、直接依存とは区別して意図を決めます。`go list -test` ではテスト用パッケージも列挙されますが、通常の出力とは別に合成パッケージが現れるため、対象の正規化とテスト用例外を定義します。

同一 Go module 内の `internal` は、その親ディレクトリ配下からの import を制限する仕組みであり、業務モジュール間の公開面を自動では守りません。例えば `internal/catalog` と `internal/billing` が同じ親の下にあるなら、Go の `internal` だけでは片方が他方の内部パッケージを参照することを防げません。`catalog` が公開する `internal/catalog/api` だけを `billing` からの参照先として許可し、それ以外を禁止するルールを設けられます。実際のパスは自分たちの構成に合わせ、接頭辞の部分一致ではなくパス区切りを考慮します。

データ所有も同様です。例えば請求側が読書記録側のテーブルを直接更新しないと決めた場合、SQL アクセスを限定した adapter に集約し、その adapter への参照や DB 権限を検査します。動的 SQL、別サービスや共有資格情報によるアクセスは import 検査では見えません。権限の確認、契約テスト、レビューを組み合わせます。

## Context、Outbox、Observability の検証

Context のルールは処理寿命を対象にします。リクエストから起動する DB や外部呼び出しには受け取った `context.Context` を渡し、期限切れやキャンセルを下流へ伝えます。独立して動く worker はリクエストの Context を保持せず、プロセスの終了に結び付いた Context を使います。例えば adapter 内で `context.Background()` を新たに作る箇所を analyzer で候補として報告し、正当なプロセス起点は明示的に扱います。構文だけでは Context の由来や、ドライバーが実際にキャンセルに反応するかは保証できません。第21章のキャンセルテストと shutdown テストで実行時の振る舞いも確かめます。

Outbox では、業務データの更新と送信予定レコードを同じ DB トランザクションで確定することを検証します。保存失敗や commit 前の障害で両方が残らないこと、成功時には両方が残ることを実 DB で確かめます。送信成功後に送信済みの記録が失敗すると再送され得るため、受信側の冪等処理も別にテストします。静的解析でトランザクション API の利用を促せても、原子性や外部配信の成否は証明できません。

Observability では、HTTP から下流呼び出しへの trace context の伝播、エラー時の span 状態、処理件数や失敗件数の計測をテストします。非同期処理は伝播情報をメッセージに保存・復元する方式を決め、機密情報を含めないことも確認します。ログやメトリクスにユーザー ID などの高カーディナリティな値を無制限にラベルとして付けないこともルール候補です。実際に必要な情報が得られるかは、運用時のダッシュボードや障害訓練でも評価します。サンプリングにより全 trace が保存されるとは限りません。

## 標準ツール、lint、custom analyzer の使い分け

- `go list` はパッケージと依存グラフの取得に適しています。第4章の例のように小さな禁止関係から始めます。
- `go vet` は標準の解析器によって疑わしいコードを検出します。アーキテクチャの独自ルールを標準設定だけで網羅するものではありません。
- lint は既存の import 制約やコード規約を表現できる場合に有効です。設定形式やマッチ方法はツールとバージョンに依存するため、固定したバージョンの文書を参照し、許可・違反の両例で確認します。
- custom analyzer は既存のルールで表現できない検査に使います。型情報や呼び出し関係を利用できます。Go の `go/analysis` を使い、診断位置、理由、修正方法を示します。解析器自体にも正常例、違反例、境界例のテストを用意します。

例えば `adapter` 内の `context.Background()` を報告する analyzer を考えます。文字列検索ではなく `go/types` で呼び出し先を特定すると、import の別名にも対応できます。それでも正当なプロセス起点やラッパー経由の呼び出しは別途扱う必要があります。独自解析は保守費用がかかるため、既存の検査で十分かを先に確認します。

## CI に組み込む

まず対象モジュールのルートで、次のように高速な検査と実 DB が必要な検査を分けます。`./scripts/check-dependencies.sh` と `./tools/archvet`、`integration` タグ付きテストは、チームが用意したものを示す例です。第4章のコマンドをスクリプトに保存し、権限を設定して使えます。

```bash
./scripts/check-dependencies.sh
go vet ./...
go test ./...
go build -o ./bin/archvet ./tools/archvet
go vet -vettool=./bin/archvet ./...
go test -tags=integration ./...
```

CI では Go と lint のバージョンを固定し、実 DB 用の隔離された環境とスキーマを用意します。単一モジュールの `./...` はネストした別モジュールを網羅しないため、各モジュールのルートでも実行します。OS、アーキテクチャ、ビルドタグで選択されるファイルが変わる場合は、対応する組み合わせを CI に追加します。テスト専用の依存や生成コードを含めるかも明示します。PR では高速な検査を必須とします。外部環境が必要な検査もマージ前に実行します。lint を採用する場合は、その固定バージョンに対応した設定で同じ CI に追加します。

## 例外とルールの更新

既存の違反が多い場合は、まず一覧を作り、新規違反を防ぎながら段階的に減らします。一時的な例外は対象パスとルール、理由、責任者、期限、追跡先を記録し、期限切れを検出できるようにします。例えば移行中の旧 adapter 1つだけを期限付きで許可します。移行完了後は例外とテストを削除します。ディレクトリ全体やテスト全体の無期限の除外は避けます。

誤検知は再現例を analyzer やルールのテストに追加して修正します。ルール変更時には許可・禁止の両方の例と既存の例外を見直し、影響を確認してから必須チェックに反映します。CI の失敗を無条件に無視するのではなく、検査の故障と設計上の違反を区別して対応します。

## まとめ

依存方向や公開面は静的なグラフで、Context、Outbox、Observability の重要な性質は実行時のテストや計測でも確かめます。1つのツールを正解とせず、対象範囲と限界を明示した小さな検査を継続的に育てます。
