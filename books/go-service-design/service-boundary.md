---
title: "モジュールからサービス境界へ〜分散させる前に境界を育てる〜"
---

## はじめに

前章では、変更の影響を閉じ込めるために、機能単位のモジュールを Go のパッケージとして表現しました。ここで次の疑問が生まれます。

> `book`、`reading`、`review`、`user` を、それぞれ独立したサービスに分けるべきでしょうか。

結論から言えば、**境界が見えたことと、プロセスを分けるべきことは同じではありません**。まず同一プロセス内でモジュール境界を育て、独立デプロイや障害分離が必要になった境界だけをサービスへ昇格させます。

本章では、モジュール、境界づけられたコンテキスト、プロセス、サービスを区別し、モジュラーモノリスから始める判断基準を整理します。

## この章で答える問い

- Go の package や module と、DDD の境界づけられたコンテキストは何が違うのか
- 境界づけられたコンテキストを、そのままマイクロサービスにしてよいのか
- どのような条件がそろったとき、プロセスを分けるべきか
- 分散させることで何を得て、何を失うのか

読み終えたとき、技術トレンドではなく、変更・運用・組織の要請を根拠にサービス境界を説明できることを目指します。

## 4つの「境界」を区別する

本書では、似た言葉を次のように使い分けます。

| 用語 | 本書での意味 | 主に守るもの |
| --- | --- | --- |
| package | Go のコンパイル単位。名前空間と公開範囲を作る | 実装の詳細 |
| module | ある業務能力をまとめたコード上の単位 | 変更の影響範囲 |
| 境界づけられたコンテキスト | 用語とモデルの意味が一貫する範囲 | ドメインモデルの意味 |
| service | 独立して実行・デプロイ・運用する単位 | 実行時と運用上の独立性 |

これらは1対1に対応するとは限りません。1つの境界づけられたコンテキストを複数 package で実装することも、複数モジュールを1つのプロセスで動かすこともできます。

:::message

**境界づけられたコンテキスト = マイクロサービスではありません。**

境界づけられたコンテキストはモデルの一貫性を守る境界です。マイクロサービスは、独立デプロイや障害分離などを目指す実行・運用上の境界です。目的が違うため、機械的に対応付けないようにします。

:::

## レイヤーより先に変更のまとまりを見る

レイヤー別にディレクトリを作ると、1つの機能を変更するたびに複数の場所を横断します。

```text
internal/
├── domain/
├── usecase/
├── interface/
└── infrastructure/
```

読書ログサービスでは、最初に業務上の変更のまとまりを見ます。

```text
internal/
├── book/
├── reading/
├── review/
└── user/
```

必要になったモジュールだけ、その内部をレイヤーに分けます。

```text
internal/
├── book/
│   ├── domain/
│   ├── usecase/
│   └── adapter/
├── reading/
│   ├── domain/
│   ├── usecase/
│   └── adapter/
├── review/
└── user/
```

この構成の狙いは、ディレクトリをきれいに見せることではありません。たとえば読了記録の仕様変更を `reading/` の中に閉じ込め、レビュー投稿の変更と不必要に混ぜないことです。

## まずモジュラーモノリスとして始める

コード上の境界を保ちながら、デプロイ単位は1つにした構成を、ここではモジュラーモノリスと呼びます。

```text
                 1 process / 1 deployment

┌─────────────────────────────────────────────┐
│ BookLog                                     │
│                                             │
│  book ── reading ── review ── user          │
│   │          │          │        │          │
│ public API / event / explicit dependency    │
└─────────────────────────────────────────────┘
```

同一プロセスに置くことで、次の単純さを保てます。

- 関数呼び出しで連携できる
- 1つのローカルトランザクションを使える
- 分散トレーシングなしでも処理を追いやすい
- ローカル環境を簡単に起動できる
- デプロイ、監視、障害対応の対象が少ない

一方で、同じプロセスにあるからといって、別モジュールの内部実装を自由に import してよいわけではありません。公開 API、明示的な port、ドメインイベントなど、合意した境界だけを通して連携します。

## モジュール間連携を明示する

### 同期呼び出し

結果がその場で必要なら、利用側が必要とする小さな interface を定義します。

```go
package reading

type BookFinder interface {
    Exists(ctx context.Context, bookID string) (bool, error)
}

type StartReadingInteractor struct {
    books BookFinder
    repo  ReadingRepository
}
```

`reading` は `book` の内部構造ではなく、「本が存在するか」という能力だけに依存します。実装を同一プロセス内の adapter にするか、将来 HTTP クライアントにするかは外側で決めます。

### 非同期の通知

その場で結果を待たなくてよい副作用には、イベントが候補になります。

```text
reading: ReadingCompleted
             │
             ├──> review: レビュー依頼を準備
             └──> user:   読了冊数を更新
```

ただし、同一プロセスのイベント配信と、別プロセスへの信頼できる配信は同じではありません。別プロセスへ届けると、保存と送信の二重書き、再送、重複、順序、停止中の consumer といった問題が発生します。これらは第19章で扱います。

## サービス分割を検討するシグナル

次の要請が継続して現れ、モジュール境界が安定しているなら、サービス分割を検討します。

### 独立デプロイが必要

ある機能だけを高頻度で変更したい、または他機能のリリース待ちにしたくない場合です。ただし、実際には常に同時変更が必要なら、分割しても独立性は得られません。

### スケーリング特性が大きく異なる

検索だけが大量の読み取りを受ける、画像処理だけが CPU を多く使う、というように、個別に資源を増減したい場合です。

### 障害を隔離したい

推薦処理の高負荷や外部 API 障害が、書籍登録まで巻き込むことを避けたい場合です。プロセス分離だけでなく、timeout、bulkhead、rate limit なども合わせて設計します。

### データの所有者を分離したい

モジュールごとにデータの書き込み責任を明確にし、他のモジュールから直接テーブルを更新させたくない場合です。サービス分割後も共有 DB に自由に書き込めるなら、境界は実質的に分かれていません。

### チームの責任境界が安定している

チームが設計、実装、デプロイ、運用まで継続して所有できる場合です。組織図をそのまま一時的なサービス分割へ写すのではなく、長期的な変更のまとまりと一致しているかを確認します。

## 分散させることで失うもの

プロセスを分けると、関数呼び出しがネットワーク通信に変わります。

```text
関数呼び出し
    ↓
ネットワーク通信

1つの DB transaction
    ↓
複数のローカルトランザクション

即時整合性
    ↓
結果整合性を含む設計

1つのデバッガ
    ↓
ログ・メトリクス・トレースによる追跡
```

具体的には、次のコストが増えます。

- timeout と cancellation
- retry と backoff
- 部分失敗
- 重複配信と冪等性
- バージョン互換性
- サービスディスカバリと認証
- 監視、アラート、オンコール
- ローカル開発と統合テスト

「将来スケールするかもしれない」だけでは、このコストを引き受ける理由として弱すぎます。現在観測している制約と、分割によって解消したい問題を具体的にします。

## 分割判断のチェックリスト

次の問いに、証拠を添えて答えます。

| 問い                   | 分割を支持する証拠               | 分割を急がないサイン     |
| ---------------------- | -------------------------------- | ------------------------ |
| 独立して変更できるか   | API とデータ所有が安定している   | 同時変更が頻発する       |
| 独立デプロイが必要か   | リリース頻度や承認フローが異なる | いつも一緒にリリースする |
| 独立スケールが必要か   | 負荷計測で特性差が確認できる     | 将来予測だけである       |
| 障害分離が必要か       | 障害履歴と影響範囲が明確         | timeout すら未設計である |
| チームが所有できるか   | 開発から運用まで担当できる       | 運用担当が共有され過ぎる |
| 分散のコストを払えるか | Observability と自動化がある     | 手動運用が多い           |

1つ当てはまっただけで分割するのではありません。得られる独立性が、増える運用コストを上回るかを総合的に判断します。

## 境界を育ててから分割する

安全な進化は次の順序です。

```text
レイヤーだけのモノリス
        ↓
機能単位のモジュールを作る
        ↓
モジュールの公開 API とデータ所有を明確にする
        ↓
同一プロセス内で境界を検証する
        ↓
独立性が必要なモジュールだけプロセスを分ける
```

読書ログサービスなら、最初は `book`、`reading`、`review`、`user` を同一プロセスに置きます。たとえば将来、推薦処理にだけ大きな計算資源と独立したリリースサイクルが必要になったなら、その境界を抽出します。

```text
Before
┌─────────────────────────────┐
│ BookLog                     │
│ book reading review user    │
│ recommendation              │
└─────────────────────────────┘

After
┌───────────────────────┐       ┌──────────────────────┐
│ BookLog               │ event │ Recommendation      │
│ book reading review   ├──────>│ Service             │
│ user                  │       │                      │
└───────────────────────┘       └──────────────────────┘
```

分割後も、元のモジュール境界が契約設計の土台になります。モジュラーモノリスはマイクロサービスの失敗版ではなく、境界を低コストで検証する段階です。

## 分割しない判断も記録する

Architecture Decision Record などに、次の項目を残します。

```text
Decision: reading を独立サービスに分割しない

Context:
- reading と book は同時変更が多い
- 現在の負荷は単一プロセスで十分
- チームは同じオンコール体制

Consequences:
- ローカルトランザクションを維持できる
- reading の独立デプロイはできない

Revisit when:
- デプロイ頻度の差が継続する
- 負荷特性の差が計測で確認される
```

「何を分けたか」だけでなく、「なぜ今は分けないのか」と再検討条件を残すと、将来の議論を感覚論に戻さずに済みます。

## まとめ

- package、module、境界づけられたコンテキスト、service は目的の異なる境界です
- 境界づけられたコンテキストを、そのままマイクロサービスへ対応付けません
- まずモジュラーモノリスでコードとモデルの境界を検証します
- 独立デプロイ、負荷、障害、データ所有、チーム責任に具体的な要請が出たときだけ分割を検討します
- 分散すると、ローカルトランザクションと単純な関数呼び出しを失い、部分失敗と運用コストを引き受けます
- 分割しない判断にも、根拠と再検討条件を残します

次章からは、この境界の内側に置くドメインモデルを設計します。後半では、処理の寿命、プロセスを越えるイベント配信、Observability を順に扱い、分散させたときに増える責務を回収します。
