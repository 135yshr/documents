## 第25章：壊れ方から設計を確かめる

第23章と第24章の読書ログサービスで、`CompleteReading` から `ReadingCompleted` の後続処理までを一続きで考えます。ここでは Context、終了処理、Outbox と冪等性、ログとトレースを統合し、遅延の原因を調べます。

`example/booklog` は標準ライブラリとインメモリのトランザクション／Outbox を使う学習用サンプルです。`slog`、HTTP、worker、シグナルによる終了を扱いますが、永続 DB、メッセージブローカー、OpenTelemetry SDK やトレース収集基盤を備えた本番環境ではありません。以下でそれらを使う部分は、導入時の設計例として読んでください。サンプルだけで DB 遅延や分散トレースを観測できるとは限りません。

このサンプルを終えても、本番運用が可能になるわけではありません。本番では、永続 DB、migration、backup と restore、secret 管理、認証と認可、キャパシティ計画、SLO と alerting、デプロイ戦略、セキュリティ、災害復旧など、本書の範囲外の準備が別途必要です。本章は、これらを検討するための観点を壊れ方の観測から示すものです。

## リクエストと worker の寿命を分ける

HTTP リクエストの Context はハンドラから `CompleteReading`、保存処理まで伝播させます。クライアント切断や期限切れが起きたら、待機中の I/O を中止できるようにするためです。集約の状態遷移そのものに Context は不要です。

worker は HTTP 応答後も配送するため、個々のリクエストではなくアプリケーションの寿命にひも付けます。リクエストの Context を worker に渡すと、応答終了時のキャンセルで配送まで中断されかねません。実運用では処理単位に別途 timeout を設け、無期限の待機を防ぎます。サンプルの worker は処理単位の timeout を設けていません。親の残り時間より長い timeout を設定しても、親の期限を延長できません。

終了シグナルを受けたら、新しい受付を止め、進行中の HTTP 処理と worker を所定の期限内に終わらせます。`http.Server.Shutdown` には、既にキャンセルされたシグナル用 Context ではなく、新たに期限を設けた Context を使います。worker の停止を待つ責任は起動側に置き、期限切れ時の扱いも決めます。強制終了や期限超過はあり得るため、途中のイベントが次回再処理されても安全な設計が必要です。インメモリでは再起動後にイベント自体が残らない点にも注意してください。

## 読了と配送の失敗を追う

正常時の流れと、失敗したときの扱いを整理します。

| 時点 | 確認すること |
| --- | --- |
| 読了処理中 | `Reading` の変更と `ReadingCompleted` の Outbox 記録を同じトランザクションで確定します |
| 確定前に失敗 | 状態と Outbox のどちらも残さず、呼び出し元に失敗を返します |
| 確定後、配送前に停止 | 永続 Outbox なら未配送として残し、再起動後に再試行します |
| Consumer 成功後、配送済み記録前に停止 | 同じイベントが再配送され得るため、Consumer が重複を扱います |
| Consumer が失敗 | 成功として消さず、再試行の方針に従います |

これは at-least-once 配送を前提とした設計です。Outbox だけでは exactly-once の副作用は保証できません。Consumer がイベント ID の処理済み記録と業務上の更新を別々に保存すると、その間の障害で二重実行や取りこぼしが生じます。永続 DB では両者を同一トランザクションに含め、ユニーク制約などで並行する重複処理も防ぎます。メール送信など DB 外の副作用には、送信先の冪等性機能や別の配送設計が必要です。

サンプルのインメモリ Outbox と処理済み情報は、プロセスの終了で消えます。再起動後の復旧や複数 worker による安全な取得は、永続化と協調制御を導入して初めて検証できます。実運用では再試行回数、backoff、処理不能なイベントの隔離、監視も決めます。

## ログとトレースの役割

`log/slog` の構造化ログには、処理名、結果、経過時間、イベント ID など、問題の切り分けに必要な情報を記録します。個人情報やリクエスト本文を無条件に記録せず、エラーの公開範囲にも注意します。ログは個々の出来事を調べる手掛かりです。処理時間の分布やエラー率などはメトリクスで継続的に観察します。

OpenTelemetry（OTel）のトレースを使うと、1つの処理を複数の span に分け、どこで時間を使ったかを見ることができます。サンプルに SDK を導入する必要はありません。導入する場合は、アプリケーションの起動時に SDK と exporter を設定し、HTTP、ユースケース、Repository の境界を計装します。採用するライブラリとバージョンの公式ドキュメントに従い、終了時には未送信データの flush と shutdown を期限付きで行います。ドメインを OTel SDK に依存させる必要はありません。

例えば、SDK と exporter を別途設定したアプリケーションで、ユースケースの呼び出しを次のように計装できます。これは導入例であり、サンプルに含まれるコードではありません。SDK の設定がなければ、この API の利用だけではトレースを収集できません。

```go
package instrumentation

import (
    "context"

    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/codes"
)

func TraceComplete(ctx context.Context, complete func(context.Context) error) error {
    ctx, span := otel.Tracer("booklog").Start(ctx, "CompleteReading")
    defer span.End()
    if err := complete(ctx); err != nil {
        span.RecordError(err)
        span.SetStatus(codes.Error, "complete reading failed")
        return err
    }
    return nil
}
```

HTTP の受信時には伝播ヘッダーから親 Context を抽出し、下流への呼び出しにも Context を渡します。非同期配送ではイベントのメタデータに trace context を注入し、worker が取り出して Consumer の span を関連付けます。遅延や再配送がある場合の親子関係と span link の選択は計装方針として決めます。trace ID とイベント ID は用途が異なり、trace ID を冪等性キーの代わりにはしません。伝播情報に機密情報を入れないことも重要です。

## DB 遅延を注入して診断する

以下は、永続 DB と OTel の計装・収集先を別途用意した環境での実験手順です。サンプルに DB 遅延注入 API やトレース閲覧画面が実装されているという意味ではありません。

1. まず遅延なしで読了を数回実行し、HTTP、`CompleteReading`、Repository の span の所要時間とエラー率を基準として記録します。
2. テスト環境で Repository の DB 操作に意図的な待ち時間を加えます。例えばテスト用ラッパーで Context に従って待機してから実際の DB 操作を呼びます。本番データには適用しません。
3. 同じ条件で読了し、trace 上の HTTP → ユースケース → DB 操作の時間を比較します。DB span が長くなるなら、その操作が遅延の候補です。span の重なりや待機を含む範囲にも注意します。
4. DB のクエリ計画、インデックス、接続プールの待ち時間、ロック待ちなどを別の計測で調べます。DB span が長いだけでは、クエリ自体と接続待ちのどちらが原因か断定できません。
5. ボトルネックに対応した変更を1つずつ試し、同じ負荷とデータ量で再計測します。意図的な遅延を取り除き、正常系、timeout、ロールバック、再配送も再確認します。

timeout を短くするだけでは DB を速くできません。クライアント側の待ち時間と、完了したか不明な操作の再試行にも影響するため、観測した分布と業務要件に基づいて設定します。トレースが欠けている場合は、サンプリング、Context 伝播、exporter の状態を確認してから結論を出します。

## 運用に向けた確認

- リクエストのキャンセルと worker の終了を、それぞれの寿命に沿って扱います。
- 読了状態と Outbox を原子的に確定し、再配送時の Consumer の副作用を抑えます。
- 永続化、障害復旧、複数 worker の競合、再試行と監視は、採用する基盤で追加検証します。
- ログ、メトリクス、トレースを組み合わせ、仮説と計測を繰り返します。

小さな modular monolith でも、処理の寿命と失敗時の境界を明示できます。必要が生じてプロセスを分けるときも、この章で整理したイベント、整合性、観測の契約が判断の出発点になります。
