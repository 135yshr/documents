自作の猫語プログラミング言語 **meow** には、ブラウザだけで動く Playground があります。

<https://meow.oreha.dev/playground/>

コードを書いて Run を押すと、その場で実行結果が返ってきます。サーバは一切使っていません。GitHub Pages の静的ファイルだけで動いています。

この記事では、この Playground をどう作ったかを書きます。「Go にトランスパイルする言語を、Go ツールチェインのないブラウザでどう動かすか」という問題との格闘記です。

## そもそもなぜ Playground が要るのか

meow は猫にちなんだキーワードでプログラミングできる言語です。`nyan` が変数宣言、`meow` が関数定義、`nya` が出力。詳しくは[紹介記事](https://zenn.dev/135yshr/articles/21b1fa2c9365cc)を読んでください。

問題は、猫語の言語を「ちょっと見てみたい」と思った人に `brew install` を要求するのはハードルが高すぎることです。興味の火が消える前に、ブラウザで 30 秒触ってもらいたい。それには Playground が必要でした。

## 問題: ブラウザに Go ツールチェインはない

meow の CLI はこういうパイプラインで動いています。

```text
.nyan → 字句解析 → 構文解析 → 型検査 → コード生成 → .go → go build → バイナリ
```

最後の 2 工程が問題です。コード生成の出力は Go のソースコードで、それをバイナリにするのは `go build`、つまりローカルにインストールされた Go ツールチェインです。ブラウザにはそんなものはありません。

選択肢は 2 つ考えました。

1. **サーバでコンパイルする**: コードを API に送り、サーバ側で `go build` して結果を返す。Go 公式の [Go Playground](https://go.dev/play/) はこの方式です
2. **ブラウザ内で完結させる**: コンパイルを諦めて、AST を直接実行するインタープリタを WASM で動かす

1 は任意コードをサーバで実行することになるので、サンドボックスの設計と運用が必要になります。個人の趣味プロジェクトで負うにはリスクとコストが大きすぎる。ホスティングを GitHub Pages の静的配信だけで済ませたい事情もあり、2 を選びました。

## 設計: パイプラインの最後だけ差し替える

幸い、パイプラインの前半 3 工程（字句解析・構文解析・型検査）はただの Go のライブラリで、ファイルシステムやプロセス起動に依存していません。WASM でもそのまま動きます。

差し替えが必要なのは最後だけです。「AST → Go コード → バイナリ」の代わりに、「AST を直接評価するインタープリタ」を書きました。いわゆるツリーウォーキング方式で、`pkg/interpreter` に約 800 行です。

```text
（CLI）        .nyan → lexer → parser → checker → codegen → go build → バイナリ
（Playground） .nyan → lexer → parser → checker → interpreter（その場で実行）
```

lexer / parser / checker は完全に共通です。同じ AST、同じ型情報を使うので、エラーメッセージも CLI と Playground で一致します。`Hiss! ... , nya~` という猫語のエラーもそのまま出ます。

## WASM のエントリポイント

WASM 側のエントリは 70 行ほどです。ポイントを絞って載せます。

```go
//go:build js && wasm

package main

import (
	"bytes"
	"encoding/json"
	"syscall/js"
	// lexer, parser, checker, interpreter を import
)

type result struct {
	Output string `json:"output"`
	Error  string `json:"error,omitempty"`
}

func runMeow(_ js.Value, args []js.Value) interface{} {
	source := args[0].String()

	// lexer → parser → checker は CLI と同じコード

	var buf bytes.Buffer
	interp := interpreter.New(&buf)
	interp.SetTypeInfo(ti)
	interp.SetStepLimit(10_000_000)
	if err := interp.RunSafe(prog); err != nil {
		b, _ := json.Marshal(result{Output: buf.String(), Error: err.Error()})
		return string(b)
	}

	b, _ := json.Marshal(result{Output: buf.String()})
	return string(b)
}

func main() {
	js.Global().Set("runMeow", js.FuncOf(runMeow))
	select {}
}
```

いくつか設計判断があります。

**`//go:build js && wasm`**: このファイルは WASM ビルドのときだけコンパイルされます。CLI のビルドには含まれません。

**`js.Global().Set("runMeow", ...)`**: Go の関数を JavaScript のグローバル関数として公開します。JS 側からは `runMeow(source)` と呼ぶだけです。

**`main` の `select {}`**: Go の WASM は `main` が終了するとランタイムごと停止し、公開した関数も呼べなくなります。`select {}` で永久にブロックして、プロセスを生かしたままにします。初見だと奇妙に見えますが、`syscall/js` を使うときの定石です。

**戻り値は JSON 文字列**: `js.Value` で構造体をやり取りするより、JSON 文字列 1 本で渡して JS 側で `JSON.parse` するほうが単純で壊れにくいです。

## インタープリタ側の工夫

### 出力は `io.Writer` に注入する

インタープリタは出力先を内部で決めず、コンストラクタで受け取ります。

```go
interp := interpreter.New(&buf)  // WASM では bytes.Buffer
```

CLI 用途なら `os.Stdout` を渡せばよく、WASM では `bytes.Buffer` に溜めて最後に JSON で返します。テストでも出力を検証しやすくなるので、最初からこの形にしておいてよかった設計です。

### 暴走対策はステップ上限

Playground には確実に、`purr i (1..1000000000)` のような巨大なループや、終わらない再帰を書く人が現れます。サーバならタイムアウトで殺せますが、ブラウザの WASM は実行中メインスレッドを占有するので、放っておくとタブごと固まります。

対策として、インタープリタに評価ステップの上限を入れました。

```go
interp.SetStepLimit(10_000_000)
```

1000 万ステップを超えたら実行を打ち切ってエラーを返します。FizzBuzz やフィボナッチ程度なら余裕で収まり、無限ループは数秒で止まる、という塩梅の数字です。

### `bring`（return）は panic/recover で実装

ツリーウォーキングインタープリタで関数からの早期リターンを実装する方法はいくつかあります。meow では `bring` を専用の値で panic して、関数呼び出しの境界で recover する方式にしました。評価器の各ノードに「リターン中かどうか」のフラグを引き回さずに済むので、コードが素直になります。

実行全体も `RunSafe` が recover で包んでいて、インタープリタ内部のどこで panic してもエラーメッセージとして JS 側に返ります。ブラウザのコンソールに Go のスタックトレースを吐いて死ぬ、という事態にはなりません。

## ブラウザ側は素の JavaScript

フロントエンドはフレームワークなしの JS で 100 行程度です。WASM のロードはこれだけです。

```js
async function loadWasm() {
  const go = new Go(); // wasm_exec.js が提供するクラス
  const result = await WebAssembly.instantiateStreaming(fetch("meow.wasm"), go.importObject);
  go.run(result.instance);
  wasmReady = true;
  status.textContent = "Ready";
}
```

`wasm_exec.js` は Go 公式が配布している糊で、Go ランタイムと JS の橋渡しをします。Go のインストールディレクトリからコピーするだけです。

```bash
cp "$(go env GOROOT)/lib/wasm/wasm_exec.js" playground/
```

Run ボタンは `runMeow(source)` を呼んで `JSON.parse` するだけですが、1 つだけ小細工があります。

```js
status.textContent = "Running...";
setTimeout(() => {
  const result = JSON.parse(runMeow(source));
  // 結果を表示
}, 10);
```

`runMeow` は同期実行でメインスレッドを塞ぐため、直前の「Running...」表示が画面へ反映される前に実行が始まってしまいます。`setTimeout` で 1 フレーム譲って、ステータス表示を描画させてから実行しています。Web Worker に逃がすのが正攻法ですが、ステップ上限があるので最長でも数秒しか塞がらず、この規模ならこれで十分と判断しました。

## ビルドとデプロイ

WASM のビルドは環境変数を 2 つ指定するだけです。

```bash
GOOS=js GOARCH=wasm go build -o playground/meow.wasm ./cmd/playground/
```

生成される `meow.wasm` は約 3.7MB、gzip 配信で転送量は約 1MB です。コンパイラ一式（lexer / parser / checker / interpreter / ランタイム）が入ってこのサイズなら許容範囲だと思っています。

デプロイは GitHub Actions に任せています。公式サイトは Hugo 製で、CI が Hugo のビルドと WASM のビルドを両方やり、`/playground/` 配下に成果物をまとめて GitHub Pages に上げます。main に push すれば言語の最新版が Playground に反映されます。

## 引き換えに背負ったもの: 実行系が 2 つになった

この構成には代償があります。**言語のセマンティクスを変えるたびに、codegen とインタープリタの両方を直す必要がある**ことです。

たとえば新しい組み込み関数を 1 つ足すには、コード生成では対応する Go の関数呼び出しを吐き、インタープリタでは同じ挙動を評価器に実装します。片方だけ直すと「CLI と Playground で結果が違う」という最悪のバグになります。

現状は、コンパイラ側のゴールデンテストとインタープリタ側のテストを両方 CI で回して食い止めています。それでも二重実装のコストは確かにあります。ではインタープリタを正として codegen をなくすべきだったかというと、答えは No です。ネイティブバイナリを吐けることは meow のアイデンティティなので、ここは二重実装を受け入れると決めました。

## まとめ

- Go にトランスパイルする言語のPlaygroundを、サーバなし・GitHub Pages だけで動かした
- lexer / parser / checker は CLI と共通、最後の工程だけツリーウォーキングインタープリタに差し替えた
- `syscall/js` + `js.FuncOf` で Go の関数を JS に公開し、`select {}` でランタイムを生かし続ける
- 無限ループはステップ上限（1000 万）で打ち切る
- 代償は codegen とインタープリタの二重メンテ
