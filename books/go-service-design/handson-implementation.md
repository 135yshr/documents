## 第24章：読了までの実装を追う

第23章で決めた読書ログサービスを、内側から外側へたどります。`example/booklog` は Go の標準ライブラリを使う学習用サンプルです。`Reading` 集約、`CompleteReading`、インメモリのトランザクションと Outbox、HTTP、worker を通して、状態変更から後続処理までを確認します。

完全な `book`、`reading`、`review`、`user` の各機能を実装する章ではありません。外部書誌 API、認証、感想、永続 DB、実際のメッセージブローカーや OpenTelemetry SDK もサンプルの前提ではありません。以下の図や擬似コードは理解のための説明であり、サンプルの API 定義そのものではありません。

## 1. 集約で状態を変更する

`Reading` が読了できる状態か確認し、読了状態を更新します。ハンドラが状態フィールドを直接書き換えると、別の入口から不正な遷移を許してしまいます。サンプルでは未読了から読了への変更だけを扱い、読了日時は記録しません。

読了に成功したという事実が `ReadingCompleted` です。サンプルのイベントは ID、対象の読書記録の ID、種類を持ち、発生時刻は記録しません。イベント ID と読書記録 ID は別の役割です。前者は同じイベントの再配送を識別し、後者はどの集約に起きた出来事かを示します。日時が業務上必要になれば、時計の扱いとともに追加します。

集約のテストでは、正常な読了と、既に読了しているなど遷移できない場合を確認します。エラー時には状態とイベントの両方を変えてはいけません。

## 2. ユースケースで一緒に確定する

`CompleteReading` は HTTP を知らずに、トランザクションの中で対象を取得し、集約の読了処理を呼び出し、状態とイベントを保存します。概念上の順序は次のとおりです。

```text
トランザクション開始
  読書記録を取得
  Reading を読了にする
  更新した Reading を保存
  ReadingCompleted を Outbox に記録
成功なら両方を確定、失敗なら両方を破棄
```

例えば Outbox への記録が失敗したら、読書状態だけを確定してはいけません。逆に、状態の更新が失敗したのにイベントだけを残してもいけません。イベントを直接外部へ送ってから DB を確定する方法では、この一体性を保証できません。

インメモリのトランザクションは、途中で変更したオブジェクトが共有データへ漏れないように扱い、並行実行も保護する必要があります。DB のトランザクションの考え方を学べますが、プロセスのクラッシュ後に復元できる永続性はありません。後で DB を採用するときは、両方の書き込みが本当に同じ DB トランザクションを使うことを確認します。

## 3. HTTP から呼ぶ

HTTP 層は入力を読み取り、リクエストの `Context` をユースケースへ渡し、結果を HTTP 応答に変換します。入力不備、対象なし、状態遷移の失敗、内部障害はそれぞれ契約に沿って扱います。クライアント切断や期限切れも、下流の処理へ伝えます。

サンプルの起動時には ID が `demo` の未読了記録を1件用意します。サンプルのルートから、別々のターミナルで次を実行できます。

```bash
go run ./cmd/booklog
```

```bash
curl -i -X POST http://localhost:8080/readings/demo/complete
```

正常に読了すると `204 No Content` を返し、同じ記録を再度読了すると `409 Conflict` です。存在しない ID は `404 Not Found` です。HTTP の Idempotency Key によるリクエスト再試行は実装していません。登録 API はなく、再起動するとインメモリのデータは初期化されます。

確認後はサーバーを起動したターミナルで Ctrl-C を押して終了します。サーバープロセスへの SIGTERM でも終了処理が動きます。`go run` のプロセスと実際のサーバープロセスは別の場合があるため、SIGTERM を送る際は対象を確認してください。

## 4. worker と Consumer へ渡す

worker は Outbox の未処理イベントを取得し、Consumer へ渡します。Consumer が成功した後に配送済みとして記録することで、処理前にイベントを失う危険を減らします。一方、Consumer の成功後、配送済みの記録前に失敗すれば、同じイベントを再配送する必要があります。

サンプルの Consumer はイベント ID ごとに処理済みかを確認し、カウンターを増やす処理と処理済みの記録を同じロックで保護します。学習用のインメモリ実装では、処理済み情報もプロセス終了時に失われます。実運用では後続の業務データ変更と処理済み ID の保存を同一トランザクションに含めるなど、永続的な冪等性の設計が必要です。外部サービスへの副作用を含む場合は、相手側の冪等性キーなども検討します。

## 5. 確認の進め方

サンプルのルートで、まず既存のテストを実行します。

```bash
cd books/go-service-design/example/booklog
go test ./...
```

テストと実装を読み、次の点を確認します。

1. 有効な読了では状態と Outbox のイベントが一緒に残ります。
2. 対象なしや不正な遷移では、読了イベントが増えません。
3. トランザクション途中の失敗では、状態とイベントがどちらも確定しません。
4. 同じイベントを再配送しても、Consumer の副作用を二重に実行しません。
5. HTTP の結果と worker の終了は、それぞれのテストや起動コードの契約に従います。

これらは確認したい観点です。各項目をサンプルのテストがすべて網羅しているとは限りません。不足するケースは、自分でテストを追加して確かめてください。並行性を扱うコードでは `go test -race ./...` も有用です。

次章では、同じ読了処理を停止、再配送、計測の観点から見直します。
